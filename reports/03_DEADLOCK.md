# [Bug] Deadlock - 멀티스레드 환경에서 교착상태 발생으로 프로세스 무응답

> ⚠️ **증거 데이터 출처 안내**
> 아래 수치는 `sim/fault_sim.py`(진단 연습용 시뮬레이터)로 재현한 결과입니다.
> **제출 시 실제 `agent-leak-app` 바이너리의 출력으로 교체하세요.** (`🔄` 표시)
> **3절의 교착상태 이론은 그대로 적용됩니다.**

---

## 1. Description (현상 설명)

`agent-leak-app` 실행 후 약 1초 뒤 **프로세스가 멈춥니다.**
그런데 **종료되지는 않습니다.** PID 는 그대로 살아 있고, 로그 출력만 완전히 끊깁니다.

| 항목 | 내용 |
|---|---|
| **언제** | 기동 후 약 1초 (두 스레드가 각자 첫 락을 잡은 직후) |
| **조건** | `MULTI_THREAD_ENABLE=true` |
| **PID** | **살아 있음** — 종료 메시지 없음 |
| **CPU/MEM** | 변화 없음 (0.1~0.2% 고정) |
| **로그** | `WAITING ... BLOCKED` 에서 멈춤 |

> **이 케이스가 앞의 둘과 근본적으로 다른 점:**
> OOM·CPU 는 **프로세스가 죽습니다.** 죽으면 최소한 "죽었다"는 사실은 알 수 있습니다.
> 교착상태는 **살아 있는데 아무 일도 안 합니다.** 모니터링이 "프로세스 살아 있음 ✅"
> 만 본다면 **장애를 정상으로 보고합니다.** 가장 발견하기 어려운 유형입니다.

---

## 2. Evidence & Logs (증거 자료)

### 2-1. PID 존재 증거 — "죽은 게 아니라 멈췄다" 🔄

```bash
$ ps -ef | grep agent | grep -v grep
agent  192  1  0 06:58 ?  00:00:00 python3 /home/agent/agent-app/fault_sim.py

$ ps -p 192 -o pid,stat,%cpu,%mem,etime,cmd
    PID STAT %CPU %MEM     ELAPSED CMD
    192 Sl    0.2  0.2       00:05 python3 .../fault_sim.py
```

**`STAT` 열이 핵심 증거입니다.**

| 문자 | 의미 |
|---|---|
| **`S`** | Sleeping — **대기 중** (무언가를 기다리고 있다) |
| **`l`** | multi-threaded — 멀티스레드 프로세스 |
| (`R` 이면) | Running — 실제로 일하는 중 |

`R` 이 아니라 `S` 라는 것은 **CPU 를 쓰고 있지 않다**는 뜻입니다.
무한 루프에 빠진 것이라면 `R` 이어야 합니다. **무한 루프가 아니라 무한 대기입니다.**

### 2-2. 스레드별 상태 — 전부 `futex_wait` 🔄

```bash
$ ps -L -p 192 -o pid,tid,stat,%cpu,wchan:20,comm
    PID     TID STAT %CPU WCHAN                COMMAND
    192     192 Sl    0.2 futex_wait           python3
    192     194 Sl    0.0 futex_wait           python3
    192     195 Sl    0.0 futex_wait           python3
```

> **`wchan` 이 결정적입니다.** `wchan`(wait channel)은 **커널 안에서 무엇을
> 기다리는 중인지**를 보여줍니다. `futex_wait` 는 **락(lock)을 기다리는 중**이라는
> 뜻입니다. (futex = Fast Userspace muTEX)
>
> 디스크를 기다린다면 `io_schedule`, 네트워크면 `sk_wait_data` 가 나옵니다.
> **세 스레드가 전부 `futex_wait`** — 아무도 일하지 않고 전부 락을 기다립니다.
> 이것이 교착상태의 **커널 레벨 물증**입니다.

### 2-3. CPU/MEM 정체 증거 — 3회 반복 측정 🔄

```
  1회:  0.2 0.2
  2회:  0.1 0.2
  3회:  0.1 0.2
```

2초 간격 3회 측정에서 값이 **움직이지 않습니다.**
(CPU 가 조금씩 내려가는 것은 "수명 전체 평균"이라 시간이 갈수록 희석되는 것이지,
새로 일을 한 것이 아닙니다.)

### 2-4. 마지막 로그 — 멈춘 지점 🔄

```
[06:58:11.270] [INFO] [Thread-A] Acquiring lock1...
[06:58:11.270] [INFO] [Thread-B] Acquiring lock2...
[06:58:11.270] [INFO] [Thread-A] Acquired lock1. Working...
[06:58:11.270] [INFO] [Thread-B] Acquired lock2. Working...
[06:58:12.274] [WARN] [Thread-B] WAITING for lock1... BLOCKED
[06:58:12.275] [WARN] [Thread-A] WAITING for lock2... BLOCKED
                                  ← 이후 아무 기록 없음
```

**이 6줄이 교착상태를 논리적으로 증명합니다.**

```
Thread-A : lock1 획득 ✅  →  lock2 대기 🔒 (B 가 갖고 있음)
Thread-B : lock2 획득 ✅  →  lock1 대기 🔒 (A 가 갖고 있음)
```

A 는 B 가 놓아야 진행하고, B 는 A 가 놓아야 진행합니다.
**둘 다 상대가 먼저 놓기를 기다리므로 영원히 풀리지 않습니다.**

## 3. Root Cause Analysis (원인 분석)

### 3-1. 교착상태(Deadlock)란

**둘 이상의 스레드가 서로가 가진 자원을 기다려 모두 영원히 진행하지 못하는 상태.**

대표 비유가 **식사하는 철학자들 문제**입니다. 둥근 식탁에 철학자 5명이 앉고
포크는 5개, 각자 양옆의 포크 2개를 들어야 식사할 수 있습니다. 모두가 동시에
**왼쪽 포크를 먼저 집으면**, 전원이 오른쪽 포크를 기다리며 영원히 굶습니다.
아무도 잘못한 사람이 없는데 전체가 멈춥니다.

### 3-2. 교착상태 4대 조건 — 이 장애에 모두 성립

**네 가지가 동시에 성립해야만** 교착상태가 됩니다. 하나만 깨면 발생하지 않습니다.

| 조건 | 뜻 | 이 장애에서 |
|---|---|---|
| **상호 배제**<br>Mutual Exclusion | 한 자원은 한 번에 하나만 쓸 수 있다 | `lock1`, `lock2` 는 한 스레드만 소유 가능 |
| **점유 대기**<br>Hold and Wait | 이미 쥔 채로 다른 것을 기다린다 | A 는 lock1 을 **쥔 채로** lock2 를 기다림 |
| **비선점**<br>No Preemption | 남이 쥔 것을 강제로 뺏을 수 없다 | 락은 소유자가 놓아야만 풀림 |
| **순환 대기**<br>Circular Wait | 대기 관계가 고리를 이룬다 | **A → B → A** |

```
        lock1                    lock2
          │                        │
      [Thread-A] ──대기──→ [Thread-B]
          ↑                        │
          └────────대기─────────────┘
```

### 3-3. 왜 "순서"가 원인인가

A 와 B 가 **같은 순서로** 락을 잡았다면 교착은 일어나지 않습니다.

```
A: lock1 → lock2        A: lock1 → lock2
B: lock2 → lock1  ❌    B: lock1 → lock2  ✅
   (반대 순서)              (같은 순서)
```

같은 순서면 먼저 `lock1` 을 잡은 쪽이 끝까지 진행하고, 다른 쪽은 기다렸다가
순서대로 받습니다. **고리가 생기지 않습니다.**

> 그래서 교착상태는 **"락을 잘못 썼다"기보다 "락을 잡는 순서를 정하지 않았다"** 는
> 설계 누락에 가깝습니다. 코드만 보면 양쪽 다 멀쩡해 보이는 게 함정입니다.

### 3-4. 왜 발견하기 어려운가

| | 보이는 것 | 놓치는 이유 |
|---|---|---|
| 프로세스 | **살아 있음** | "죽지 않았으니 정상"으로 오판 |
| 포트 | **LISTEN 유지** | 헬스체크가 통과해버림 |
| CPU/MEM | **낮고 안정적** | 자원 경고가 안 울림 |
| 로그 | **멈춤** | "조용하니 한가한가 보다" |

**모든 지표가 '정상'으로 보입니다.** 그래서 `monitor.sh` 의 Health Check 만으로는
교착을 못 잡습니다. **"로그가 N분째 멈춰 있다"** 같은 **무응답 감지**가 따로 필요합니다.

## 4. Workaround & Verification (조치 및 검증)

### 4-1. 조치 내용

환경변수 `MULTI_THREAD_ENABLE` 을 **`true` → `false`** 로 변경했습니다.

```bash
export MULTI_THREAD_ENABLE=false
```

단일 스레드로 동작하면 **락 경쟁 자체가 없어지므로** 교착이 성립하지 않습니다.
(4대 조건 중 **순환 대기**가 깨집니다 — 대기할 상대가 없습니다)

### 4-2. Before & After 🔄

| | Before (`true`) | After (`false`) |
|---|---|---|
| 동작 | **1초 뒤 무응답** | **정상 완료** |
| PID | 살아 있으나 멈춤 | 작업 후 정상 종료 |
| 스레드 | 3개, 전부 `futex_wait` | 1개 (Thread-Main) |
| 마지막 로그 | `WAITING ... BLOCKED` | `All tasks completed normally` |

```
# After 로그
[06:58:37.607] [INFO] [Thread-Main] Task  4/10 completed
[06:58:38.610] [INFO] [Thread-Main] Task  5/10 completed
...
[06:58:43.634] [INFO] [Thread-Main] Task 10/10 completed
[06:58:44.640] [INFO] [Worker] All tasks completed normally. Exiting.
```

**10개 작업을 전부 끝내고 정상 종료**했습니다.

### 4-3. 검증 결과 해석

> **교착은 사라졌지만, 병렬 처리도 함께 사라졌습니다.**
> 단일 스레드는 **작업을 하나씩 순서대로** 처리하므로, 처리량이 스레드 수만큼
> 떨어집니다. 위 로그에서도 10개 작업에 약 10초가 걸렸습니다.
>
> 즉 이 조치는 **"동시성을 포기해서 안정성을 산 것"** 입니다.
> 트래픽이 적다면 쓸 만한 임시 조치지만, 처리량이 중요한 서비스에서는
> 다른 장애(응답 지연)로 바뀔 뿐입니다.

### 4-4. 근본적 해결 제안

4대 조건 중 **하나만 깨면** 교착이 발생하지 않습니다. 현실적인 순서대로:

| 우선순위 | 방법 | 깨는 조건 | 설명 |
|---|---|---|---|
| **1** | **락 순서 통일** | 순환 대기 | 모든 스레드가 **항상 같은 순서**로 락을 잡게 한다. 가장 확실하고 비용이 없다 |
| 2 | **타임아웃** | 점유 대기 | `acquire(timeout=N)`. 못 잡으면 **가진 것을 놓고 물러난다**. 영원히 멈추진 않는다 |
| 3 | **락 한 개로 합치기** | 상호 배제 | 보호할 자원이 늘 함께 쓰인다면 락을 하나로. 단순하지만 병렬성이 준다 |
| 4 | **무응답 감지 추가** | (탐지) | 해결은 아니지만, **로그가 N분째 멈추면 경고**. 발견 시간을 줄인다 |

> **1번을 가장 먼저 해야 합니다.** 코드 몇 줄만 바꾸면 되고 성능 손해가 없습니다.
> "락은 항상 lock1 → lock2 순서로 잡는다"를 **팀 규칙으로 문서화**하는 것이
> 실무에서 가장 흔한 해법입니다.

### 4-5. 재현 방법

```bash
./run.sh case deadlock true     # Before — 무응답
./run.sh diagnose deadlock      # ps -L, wchan, 정체 확인
./run.sh case deadlock false    # After  — 정상 완료
```
