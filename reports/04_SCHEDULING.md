# [Analysis] 로그 패턴 분석을 통한 스케줄링 알고리즘 추론

> 보너스 과제. **코디세이 제공 바이너리 `agent-leak-app-arm64`** 의 정상 실행
> 로그를 분석했습니다. 측정 일시 **2026-11-07 10:07:18~10:08:27 (KST)**,
> 환경 Docker `agent-triage` (Ubuntu, aarch64, 8코어).
> 분석 도구: `bin/sched_analyze.sh`

> ### ⚠️ 초안의 결론을 뒤집었습니다
> 이 리포트 초안은 **라운드 로빈**이라고 결론 내렸습니다.
> 실제 바이너리를 측정한 결과는 **FCFS(순차 처리)** 입니다. 정반대입니다.
> 초안은 진단 연습용으로 직접 만든 `sim/fault_sim.py` 의 거동을 본 것이었고,
> 그 시뮬레이터는 스레드를 번갈아 진행시키도록 제가 작성했기 때문입니다.
> **아래 3-2 에 어떻게 갈렸는지 적었습니다.**

## 1. 로그 관찰 개요

정상 실행 설정(`MEMORY_LIMIT=512` · `CPU_MAX_OCCUPY=20` · `MULTI_THREAD_ENABLE=false`)으로
띄우면 앱이 스스로 시나리오를 고르고, **작업 스케줄러 블록**을 로그에 남깁니다.

```
2026-11-07 10:07:20,982 [INFO] >>> Scenario Selected: [Healthy System Monitoring]
2026-11-07 10:07:20,991 [INFO] [Scheduler] Task Scheduler Initialized.
2026-11-07 10:07:20,992 [INFO] [Scheduler] Registered Tasks: ['Thread-A', 'Thread-B', 'Thread-C']
2026-11-07 10:07:20,992 [INFO] [Scheduler] Starting task execution...
```

관찰 대상: **스레드 3개(A/B/C)** 가 각각 20%→100% 5단계 작업을 수행하며 남기는 로그
수집 방법: 타임스탬프를 **밀리초까지** 기록. 초 단위로는 교체가 안 보입니다.
로그 위치: `/var/log/agent-app/agent_app.log` (총 75줄)

> ⚠️ **`MULTI_THREAD_ENABLE=true` 로는 이 분석을 할 수 없습니다.**
> 그 설정은 다른 시나리오(`Initializing concurrent transaction processors`)로 분기해
> `Worker-Thread-1/2` 가 2초 만에 교착에 빠집니다(리포트 03). 스케줄러 블록이 안 나옵니다.

## 2. 증거 자료

### 2-1. 로그 스냅샷 — 한 스레드가 끝나고 다음이 시작합니다

```
10:07:20,992 [INFO] [Thread-A] Task Started. Calculating... (20%)
10:07:21,047 [INFO] [Thread-A] Calculating... (40%)
10:07:21,103 [INFO] [Thread-A] Calculating... (60%)
10:07:21,154 [INFO] [Thread-A] Calculating... (80%)
10:07:21,207 [INFO] [Thread-A] Task Completed. (100%)      ← A 가 끝난 뒤에야
10:07:21,262 [INFO] [Thread-B] Task Started. Calculating... (20%)   ← B 가 시작
10:07:21,318 [INFO] [Thread-B] Calculating... (40%)
10:07:21,374 [INFO] [Thread-B] Calculating... (60%)
10:07:21,426 [INFO] [Thread-B] Calculating... (80%)
10:07:21,481 [INFO] [Thread-B] Task Completed. (100%)      ← B 가 끝난 뒤에야
10:07:21,534 [INFO] [Thread-C] Task Started. Calculating... (20%)   ← C 가 시작
10:07:21,588 [INFO] [Thread-C] Calculating... (40%)
10:07:21,643 [INFO] [Thread-C] Calculating... (60%)
10:07:21,699 [INFO] [Thread-C] Calculating... (80%)
10:07:21,755 [INFO] [Thread-C] Task Completed. (100%)
10:07:21,807 [INFO] [Scheduler] All tasks completed.
```

**세 블록이 완전히 분리돼 있습니다.** A 의 로그 5줄이 연속으로 나온 뒤 B,
그 다음 C 입니다. 섞인 줄이 **한 줄도 없습니다.**

### 2-2. 정량 분석 결과

`bin/sched_analyze.sh` 실행 결과:

```
[1] 스레드별 로그 건수
          5 Thread-C
          5 Thread-B
          5 Thread-A          ← 완전히 균등

[2] 실행 순서 (등장 순서대로 나열)
    Thread-A Thread-A Thread-A Thread-A Thread-A Thread-B Thread-B Threa
    d-B Thread-B Thread-B Thread-C Thread-C Thread-C Thread-C Thread-C

[3] 교체(context switch) 횟수 — 직전과 다른 스레드가 나온 횟수
    전체 15건 중 교체 2회 (13.3%)

[4] 진행률 끼어듦 검사
    끼어듦 없음 → 순차 처리(FCFS) 가능성

[5] 결론
    스레드 3개, 최다 5건 / 최소 5건 → 고르게 분배됨 (우선순위 편중 없음)
    판단 보류 — 샘플을 더 모으세요
```

**교체 2회는 3개 블록에서 나올 수 있는 최소값입니다** (A→B, B→C).
스레드가 3개면 적어도 두 번은 바뀌어야 하니, **필요한 최소한만 바뀐** 셈입니다.

> ⚠️ **집계에서 한 줄을 빼야 했습니다.**
> `[Scheduler] Registered Tasks: ['Thread-A', 'Thread-B', 'Thread-C']` 는
> 한 줄에 세 스레드 이름이 다 들어 있어서, 그대로 세면 실행 순서 맨 앞에
> `A B C` 가 붙고 교체 횟수가 5회(27.8%)로 부풀었습니다.
> `sched_analyze.sh` 에서 이 줄을 제외하도록 고쳤습니다.
>
> 도구가 `[5]` 에서 **"판단 보류 — 샘플을 더 모으세요"** 라고 한 것은
> 교체율이 낮아 라운드 로빈 조건에 안 맞는데, 균등 분배라서 우선순위도 아니기
> 때문입니다. **이 보류 상태에서 결론을 내리는 것이 2-3·3-1 의 일입니다.**

### 2-3. 시간 간격 — 55ms 는 '할당량'이 아니라 '작업 단계' 간격입니다

진행률 한 단계당 간격을 재면 이렇습니다.

| 구간 | 간격 |
|---|---|
| Thread-A 20% → 40% | 55ms |
| 40% → 60% | 56ms |
| 60% → 80% | 51ms |
| 80% → 100% | 53ms |
| **A 100% → B 20%** | **55ms** |

**핵심은 마지막 행입니다.** 스레드가 바뀌는 지점의 간격(55ms)이
같은 스레드 안의 단계 간격(51~56ms)과 **똑같습니다.**

| 해석 | 성립하는가 |
|---|---|
| 55ms 가 **시간 할당량**(time quantum)이라면 | ❌ 할당량마다 스레드가 바뀌어야 하는데, 5단계 내리 같은 스레드다 |
| 55ms 가 **작업 한 단계에 걸리는 시간**이라면 | ✅ 단계마다 55ms 걸리고, 5단계 끝나면 다음 스레드로 넘어간다 |

즉 **55ms 주기는 스케줄링의 증거가 아니라 작업 단위의 크기**입니다.
초안은 이 규칙성을 "할당량의 존재"로 읽었는데, **스레드 전환 지점과
단계 전환 지점이 구별되지 않는다는 점**을 놓친 것입니다.

전체 3개 작업이 `10:07:20,992` → `10:07:21,807` 약 **815ms** 에 끝났습니다.

## 3. 패턴 분석 및 결론

### 3-1. 후보를 하나씩 배제합니다

| 알고리즘 | 예상되는 패턴 | 관측 결과 | 판정 |
|---|---|---|---|
| **FCFS**<br>(First Come First Served) | A 가 100% 까지 간 뒤 B 시작 | **끼어듦 0회.** A 5줄 → B 5줄 → C 5줄 완전 분리. 교체 2회(최소값) | ✅ **부합** |
| **Round-Robin**<br>(시간 할당량 순환) | 일정 시간씩 번갈아,<br>잦은 교체 | 교체율 **13.3%** 로 최소값. 55ms 주기는 작업 단계 간격(2-3) | ❌ **배제** |
| **Priority**<br>(우선순위) | 특정 스레드가 자원 독점,<br>로그 건수 편중 | A/B/C **5건씩 완전 균등**. 독점하는 스레드 없음 | ❌ **배제** |

### 3-2. 결론

> **FCFS(First Come First Served, 선입선출)** 로 추론됩니다.

근거 세 가지:

1. **끼어듦이 전혀 없다** — Thread-A 가 `Task Completed. (100%)` 를 찍은 **뒤에**
   Thread-B 가 `Task Started` 를 찍습니다. 15개 작업 로그에서 교차가 한 번도 없습니다.
2. **교체가 최소값이다** — 3개 블록이면 최소 2회 바뀌어야 하는데, 정확히 2회입니다.
   라운드 로빈이라면 할당량마다 바뀌어 교체율이 훨씬 높아야 합니다.
3. **등록 순서대로 실행된다** — `Registered Tasks: ['Thread-A', 'Thread-B', 'Thread-C']`
   의 순서와 실행 순서가 일치합니다. **먼저 등록된 것이 먼저, 끝까지** 처리됩니다.

> 각 작업이 **시작하면 끝까지 CPU 를 쥐고**, 완료 후 다음 작업에 넘기는
> 선입선출 방식으로 판단됩니다.

#### 균등 분배를 '공평'으로 착각하면 안 됩니다

`[1]` 에서 A·B·C 가 5건씩 똑같이 나온 것은 **공평하게 번갈아 썼다는 뜻이 아닙니다.**
세 작업이 **같은 크기**(5단계)여서 각자 똑같은 만큼의 로그를 남긴 것입니다.
순서대로 하나씩 처리했어도 건수는 같게 나옵니다.

**이것이 초안이 라운드 로빈으로 오판한 지점입니다.** 균등 분배는
라운드 로빈의 특징이기도 하지만, **작업 크기가 같은 FCFS 에서도 똑같이 나타납니다.**
둘을 가르는 것은 건수가 아니라 **순서(끼어듦 여부)** 입니다.

### 3-3. 한 가지 단서 더 — 파이썬이라면 GIL

이 앱은 `stripped` 바이너리라 내부를 볼 수 없고 과제 제약에
**「디컴파일 및 리버스 엔지니어링 금지」** 가 있어 구현 언어를 단정할 수 없습니다.
다만 로그 형식(`[INFO]`, `2026-11-07 10:07:20,992` 의 쉼표 밀리초)이
**파이썬 `logging` 모듈의 기본 포맷과 같고**, `Registered Tasks: ['Thread-A', ...]` 가
**파이썬 리스트 표기**라서 파이썬 기반으로 **추정**됩니다.

파이썬이라면 **GIL(Global Interpreter Lock)** 이 작용합니다. 한 번에 한 스레드만
바이트코드를 실행할 수 있고, 일정 간격마다 GIL 을 놓아 다른 스레드에 넘깁니다.

**그런데 관측 결과는 FCFS 였습니다.** GIL 이 있으면 번갈아 실행될 텐데 왜
순차적일까요. 가능한 설명은 **애플리케이션이 스스로 순서를 강제했다**는 것입니다.
`[Scheduler]` 라는 자체 스케줄러를 두고 작업을 하나씩 돌리면, OS·런타임이
어떻든 로그에는 순차로 찍힙니다.

> **여기서 구분해야 할 두 층이 있습니다.**
>
> | 층 | 무엇을 정하는가 | 이 앱에서 |
> |---|---|---|
> | **OS/런타임 스케줄러** | 어느 스레드에 CPU 를 줄지 | 관측 불가 (앱이 가려버림) |
> | **애플리케이션 스케줄러** | 어느 작업을 언제 돌릴지 | **FCFS** — 로그로 확인됨 |
>
> 이 리포트가 관측한 것은 **아래쪽 층(애플리케이션 스케줄러)** 입니다.
> OS 스케줄러의 거동은 이 로그로 알 수 없습니다. 작업이 순차로 돌아가면
> 애초에 경쟁이 없어서 OS 가 선택할 일이 없기 때문입니다.

## 4. 장단점 및 적합한 아키텍처 분석

### 4-1. FCFS 의 장단점

| | 내용 |
|---|---|
| **장점** | ✅ **구현이 가장 단순하다** — 큐에 넣고 순서대로 꺼내면 끝 |
| | ✅ **교체 비용이 없다** — 컨텍스트 스위칭이 최소(관측 2회). 캐시도 잘 맞는다 |
| | ✅ **전체 처리량이 높다** — 교체에 쓰는 시간이 순수 작업에 들어간다 |
| | ✅ **순서가 예측 가능하다** — 등록 순서대로 끝난다. 디버깅과 로그 추적이 쉽다 |
| **단점** | ❌ **호송 효과(Convoy Effect)** — 앞에 긴 작업이 있으면 뒤의 짧은 작업이 전부 기다린다 |
| | ❌ **평균 대기 시간이 길다** — 짧은 작업도 긴 작업 뒤에 서면 오래 기다린다 |
| | ❌ **응답성이 나쁘다** — 내 차례가 언제 올지 앞 작업들이 끝나봐야 안다 |
| | ❌ **긴급 작업을 먼저 처리할 수 없다** — 순서가 유일한 기준이다 |

**호송 효과가 FCFS 의 핵심 약점입니다.**

```
작업 A(10초) → 작업 B(0.1초) → 작업 C(0.1초)  로 들어오면
  FCFS:        A 끝(10초) → B(10.1초) → C(10.2초)   평균 대기 6.7초
  짧은 것 먼저: B(0.1) → C(0.2) → A(10.2초)          평균 대기 0.1초
```

같은 작업인데 **순서만 바꿔도 평균 대기가 60배** 차이납니다.
고속도로에서 느린 트럭 한 대가 뒤차를 모두 묶어두는 것과 같아서 호송 효과라 부릅니다.

### 4-2. 어떤 서비스에 적합한가

| 서비스 성격 | 적합한 스케줄링 | 이유 |
|---|---|---|
| **처리량이 중요**<br>(배치, 데이터 집계, 빌드) | ✅ **FCFS** | 작업을 **끝까지 처리**하는 게 유리하다. 교체 비용이 순수 낭비이고 캐시도 잘 맞는다 |
| **실시간 응답이 중요**<br>(웹 서버, 채팅, API) | ❌ FCFS 부적합<br>→ **Round-Robin** | 모든 요청이 **빠르게 첫 응답**을 받아야 한다. 한 요청이 오래 걸려도 다른 요청이 막히면 안 된다 |
| **마감이 있는 작업**<br>(영상 인코딩, 제어 시스템) | ❌ FCFS 부적합<br>→ **Priority / EDF** | 급한 것을 **먼저** 해야 한다. 순서대로면 마감을 놓친다 |
| **작업 길이가 들쭉날쭉** | ❌ FCFS 부적합<br>→ **SJF** | 짧은 것부터 처리하면 평균 대기가 크게 줄어든다 |

### 4-3. 이 애플리케이션에는 적합한가

> **엄밀히 말하면 부적합합니다. 다만 지금 구조에서는 문제가 드러나지 않습니다.**

**부적합하다고 보는 이유.**
`agent-leak-app` 은 `Agent listening at port 15034` 를 찍는 **서버형** 프로그램입니다.
여러 요청이 들어올 때 **한 요청이 다른 요청을 막지 않는 것**이 중요한데,
FCFS 는 정확히 그 반대 성질을 가집니다(호송 효과). 무거운 요청 하나가
들어오면 그 뒤의 모든 요청이 대기합니다.

**그런데 지금은 문제가 안 되는 이유.**
관측된 세 작업은 **크기가 똑같습니다**(각 5단계, 약 215ms).
호송 효과는 **작업 길이가 들쭉날쭉할 때만** 나타나므로, 균일한 작업만
들어오는 한 FCFS 로도 평균 대기가 나빠지지 않습니다.
실제로 3개 작업이 815ms 에 전부 끝났습니다.

**그래서 판단은 조건부입니다.**

| 조건 | 판단 |
|---|---|
| 작업 크기가 균일하고 내부 배치 작업만 돈다면 | FCFS 로 충분하다. 단순하고 처리량도 좋다 |
| 외부 요청을 받고 처리 시간이 들쭉날쭉하다면 | **Round-Robin 또는 작업 큐 분리가 필요하다** |

> **포트를 열어둔다는 사실이 후자를 시사합니다.** 다만 이번 측정에서는
> 외부 요청을 보내 보지 않았으므로(관제·로그 분석만 했습니다),
> **요청이 섞였을 때 어떻게 되는지는 확인하지 못했습니다.**
> 확인하려면 15034 포트로 길이가 다른 요청을 동시에 보내 응답 순서를 봐야 합니다.

### 4-4. 개선 제안

| 우선순위 | 제안 | 설명 |
|---|---|---|
| **1** | **긴 작업과 짧은 작업의 큐 분리** | 호송 효과를 가장 싸게 없앤다. 짧은 요청용 큐를 따로 두면 무거운 작업 뒤에 묶이지 않는다 |
| 2 | **작업 단위 쪼개기** | 5단계를 한 번에 돌리지 않고 단계마다 양보하면 FCFS 라도 라운드 로빈처럼 동작한다 |
| 3 | **무거운 작업은 별도 워커 프로세스로** | 파이썬이라면 GIL 때문에 **스레드가 아니라 프로세스**로 분리해야 실제 병렬이 된다 |
| 4 | **대기 시간 지표 수집** | 지금 로그에는 작업 **실행** 시간만 있고 **대기** 시간이 없다. 호송 효과를 관측하려면 "큐에 들어온 시각"을 찍어야 한다 |

## 5. 재현 방법

```bash
./run.sh up
./run.sh case normal    # 정상 시나리오 — Scheduler 블록이 나온다
./run.sh sched          # 패턴 분석 실행
```

로그를 직접 보려면:

```bash
D=/Applications/OrbStack.app/Contents/MacOS/xbin/docker
$D exec agent-triage grep -E 'Scheduler|Thread-[ABC]' /var/log/agent-app/agent_app.log
```

> **주의 두 가지.**
> ① `MULTI_THREAD_ENABLE=true` 로는 스케줄러 블록이 안 나옵니다 (1절 참고).
> ② 로그 파일은 `agent_app.log` 입니다. `app.log` 가 아닙니다 — 제공 바이너리와
> 연습용 시뮬레이터가 **서로 다른 파일명**을 쓰기 때문에 `sched_analyze.sh` 가
> 둘 다 찾도록 고쳐뒀습니다.

> `bin/sched_analyze.sh` 는 **근거(수치)만 모아줍니다.** 결론은 직접 써야 합니다.
> 도구가 "FCFS 입니다" 하고 끝내면 **설명할 수 있는 능력**이 남지 않기 때문입니다.
> 실제로 이번에 도구는 `[5]` 에서 **판단을 보류**했고, 결론은 2-3 의 시간 간격
> 해석으로 직접 내렸습니다.
