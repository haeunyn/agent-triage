# [Analysis] 로그 패턴 분석을 통한 스케줄링 알고리즘 추론

> 보너스 과제. `sim/fault_sim.py --normal` 의 정상 실행 로그를 분석했습니다.
> 🔄 **제출 시 실제 바이너리의 로그로 교체**하면 같은 분석이 그대로 적용됩니다.
> 분석 도구: `bin/sched_analyze.sh`

---

## 1. 로그 관찰 개요

`agent-leak-app` 의 정상 실행 상태에서 워커(Worker) 스레드들의 작업 로그를 수집해,
OS 또는 런타임이 작업을 처리하는 **스케줄링 기법을 역추적**했습니다.

관찰 대상: 스레드 3개(A/B/C)가 각각 10단계(10%~100%) 작업을 수행하며 남기는 로그
수집 방법: 타임스탬프를 **밀리초까지** 기록. 초 단위로는 교체가 안 보입니다.

---

## 2. 증거 자료

### 2-1. 로그 스냅샷 🔄

```
[06:58:44.891] [Thread-A] Calculating... (10%)
[06:58:44.891] [Thread-B] Calculating... (10%)   ← A 가 끝나기 전에 B 시작
[06:58:44.891] [Thread-C] Calculating... (10%)   ← B 가 끝나기 전에 C 시작
[06:58:44.944] [Thread-A] Calculating... (20%)   ← C 중단, A 재개
[06:58:44.944] [Thread-B] Calculating... (20%)
[06:58:44.944] [Thread-C] Calculating... (20%)
[06:58:44.996] [Thread-C] Calculating... (30%)
[06:58:44.999] [Thread-A] Calculating... (30%)
[06:58:44.999] [Thread-B] Calculating... (30%)
[06:58:45.048] [Thread-C] Calculating... (40%)
[06:58:45.054] [Thread-A] Calculating... (40%)
[06:58:45.055] [Thread-B] Calculating... (40%)
```

### 2-2. 정량 분석 결과 🔄

`bin/sched_analyze.sh` 실행 결과:

```
[1] 스레드별 로그 건수
         11 [Thread-C]
         11 [Thread-B]
         11 [Thread-A]          ← 완전히 균등

[2] 실행 순서
    Thread-A Thread-C Thread-B Thread-A Thread-B Thread-C Thread-A
    Thread-C Thread-B Thread-A Thread-B Thread-C ...

[3] 교체(context switch) 횟수
    전체 33건 중 교체 31회 (93.9%)

[4] 진행률 끼어듦 검사
    끼어듦 26회 관측 → 순차 처리(FCFS)가 아니다

[5] 결론
    스레드 3개, 최다 11건 / 최소 11건 → 고르게 분배됨 (우선순위 편중 없음)
    교체가 잦고 분배가 고르다 → Round-Robin 으로 추론
```

### 2-3. 시간 간격

진행률 한 단계당 약 **50ms** 간격이 일정하게 유지됩니다
(44.891 → 44.944 → 44.996 → 45.048). 이 **규칙적인 주기**가 중요한 단서입니다.

---

## 3. 패턴 분석 및 결론

### 3-1. 후보를 하나씩 배제합니다

| 알고리즘 | 예상되는 패턴 | 관측 결과 | 판정 |
|---|---|---|---|
| **FCFS**<br>(First Come First Served) | A 가 100% 까지 간 뒤 B 시작 | **끼어듦 26회** 관측.<br>A 가 20% 일 때 B·C 가 이미 진행 중 | ❌ **배제** |
| **Priority**<br>(우선순위) | 특정 스레드가 자원 독점,<br>로그 건수 편중 | A/B/C **11건씩 완전 균등**.<br>독점하는 스레드 없음 | ❌ **배제** |
| **Round-Robin**<br>(시간 할당량 순환) | 일정 시간씩 번갈아,<br>고른 분배, 잦은 교체 | **교체율 93.9%**,<br>균등 분배, **50ms 규칙적 주기** | ✅ **부합** |

### 3-2. 결론

> **라운드 로빈(Round-Robin)** 으로 추론됩니다.

근거 세 가지:

1. **순차 처리가 아니다** — Thread-A 가 100% 에 닿기 전에 B 가 실행되었으므로,
   먼저 온 작업을 끝까지 처리하는 FCFS 가 아닙니다. (끼어듦 26회)
2. **우선순위 편중이 없다** — 특정 스레드가 자원을 독점하거나 긴급 처리되는 경향 없이
   A·B·C 가 **정확히 11건씩** 공평하게 나눠 가집니다.
3. **교체 주기가 규칙적이다** — 약 50ms 간격으로 일정하게 교체됩니다.
   이것이 **시간 할당량(time quantum)** 의 존재를 시사합니다.

> 각 스레드가 **정해진 시간 할당량만큼 CPU 를 사용하고 자원을 반납하는**
> 라운드 로빈 방식으로 판단됩니다.

### 3-3. 한 가지 단서 더 — 파이썬이라면 GIL

실제 바이너리가 파이썬 기반이라면, 이 패턴에는 **GIL(Global Interpreter Lock)** 도
작용합니다. 파이썬은 한 번에 한 스레드만 바이트코드를 실행할 수 있고,
일정 간격(기본 5ms)마다 **GIL 을 놓아 다른 스레드에 넘깁니다.**

이것이 OS 스케줄러 위에 얹힌 **또 하나의 라운드 로빈 층**입니다.
그래서 CPU 연산 작업은 스레드를 늘려도 빨라지지 않습니다 —
**번갈아 쓸 뿐 동시에 쓰지 못하기** 때문입니다.

## 4. 장단점 및 적합한 아키텍처 분석

### 4-1. 라운드 로빈의 장단점

| | 내용 |
|---|---|
| **장점** | ✅ **응답 시간이 예측 가능**하다 — 내 차례는 최대 (n-1)×q 안에 온다 |
| | ✅ **굶주림(starvation)이 없다** — 모두 반드시 차례를 받는다 |
| | ✅ **구현이 단순**하고 공평하다 |
| **단점** | ❌ **컨텍스트 스위칭 비용** — 교체마다 레지스터·캐시를 갈아끼운다 |
| | ❌ **전체 처리량(throughput)은 낮다** — 교체 비용이 순수 작업 시간을 깎는다 |
| | ❌ **긴급 작업을 먼저 처리할 수 없다** — 모두가 평등해서 우선순위가 없다 |

**시간 할당량(q)이 핵심 변수입니다.**

```
q 가 너무 작으면  →  교체가 너무 잦아 오버헤드가 작업 시간을 먹는다
q 가 너무 크면    →  사실상 FCFS 가 된다 (응답성 상실)
```

### 4-2. 어떤 서비스에 적합한가

| 서비스 성격 | 적합한 스케줄링 | 이유 |
|---|---|---|
| **실시간 응답이 중요**<br>(웹 서버, 채팅, API) | ✅ **Round-Robin** | 모든 요청이 **빠르게 첫 응답**을 받는다. 한 요청이 오래 걸려도 다른 요청이 막히지 않는다 |
| **처리량이 중요**<br>(배치, 데이터 집계, 빌드) | ❌ RR 부적합<br>→ **FCFS** | 작업을 **끝까지 처리**하는 게 유리하다. 교체 비용이 순수 낭비이고, 캐시도 잘 맞는다 |
| **마감이 있는 작업**<br>(영상 인코딩, 제어 시스템) | ❌ RR 부적합<br>→ **Priority / EDF** | 급한 것을 **먼저** 해야 한다. 평등하면 마감을 놓친다 |

### 4-3. 이 애플리케이션에는 적합한가

> **적합하다고 판단합니다.**
>
> `agent-leak-app` 은 포트 15034 에서 요청을 받는 **서버형** 프로그램입니다.
> 여러 요청이 들어올 때 **한 요청이 다른 요청을 막지 않는 것**이 중요하므로
> 라운드 로빈이 맞습니다.
>
> 다만 **CPU 연산이 무거운 작업이 섞인다면** 재검토가 필요합니다.
> 무거운 작업이 할당량을 계속 쓰면서 교체 비용만 늘어나므로,
> 그런 작업은 **별도 워커 프로세스로 분리**하는 편이 낫습니다.
> (파이썬이라면 GIL 때문에 **스레드가 아니라 프로세스**로 분리해야 합니다)

## 5. 재현 방법

```bash
./run.sh case normal    # 정상 동작 로그 생성
./run.sh sched          # 패턴 분석 실행
```

> `bin/sched_analyze.sh` 는 **근거(수치)만 모아줍니다.** 결론은 직접 써야 합니다.
> 도구가 "Round-Robin 입니다" 하고 끝내면 **설명할 수 있는 능력**이 남지 않기 때문입니다.
