# [Bug] CPU Spike - 과점유 방지 정책(Watchdog)에 의한 프로세스 강제 종료

> ⚠️ **증거 데이터 출처 안내**
> 아래 수치는 `sim/fault_sim.py`(진단 연습용 시뮬레이터)로 재현한 결과입니다.
> **제출 시 실제 `agent-leak-app` 바이너리의 출력으로 교체하세요.** (`🔄` 표시)
> **3절·4절의 OS 동작 원리는 그대로 적용됩니다.**

---

## 1. Description (현상 설명)

`agent-leak-app` 실행 후 CPU 사용률이 서서히 상승하다가, 임계치에 닿는 순간
`>>> [SYSTEM] WATCHDOG: INITIATING EMERGENCY ABORT (SIGTERM) <<<` 메시지와 함께
프로세스가 종료됩니다.

| 항목 | 내용 |
|---|---|
| **언제** | `CPU_MAX_OCCUPY=20` 기준 기동 후 약 **8초** |
| **조건** | CPU 사용률이 `CPU_MAX_OCCUPY` 에 도달 |
| **종료 코드** | 143 (= 128 + 15, **SIGTERM**) |
| **메모리** | 0.2% 로 **변화 없음** → 메모리와 무관 |

> **OOM 케이스와의 결정적 차이: 종료 신호가 다릅니다.**
> OOM 은 **SIGKILL(9)**, CPU 는 **SIGTERM(15)** 입니다.
> SIGTERM 은 "정리하고 나가라"는 **정중한 요청**이고, SIGKILL 은 "즉시 중단"입니다.
> 종료 코드만 봐도 어느 정책이 작동했는지 구분할 수 있습니다.

## 2. Evidence & Logs (증거 자료)

### 2-1. monitor.sh 관제 로그 — 특정 프로세스의 CPU 급상승 🔄

```
[2026-10-31 06:55:17] PROCESS:fault_sim.py PID:3960 CPU:0.0%  MEM:0.0% DISK:1% ...
[2026-10-31 06:55:20] PROCESS:fault_sim.py PID:-    CPU:-     MEM:-    ... STATE:NOT_RUNNING
```

```
# CPU_MAX_OCCUPY 를 100 으로 올려 더 오래 관측한 구간
[06:55:37] PROCESS:fault_sim.py PID:4037 CPU:101.1% MEM:0.2% DISK:1% ...
```

> **CPU 가 100% 를 넘는 것이 오류가 아닙니다.** 리눅스에서 프로세스 CPU 사용률은
> **코어 1개 = 100%** 기준입니다. 4코어 장비라면 한 프로세스가 최대 400% 까지
> 나올 수 있습니다. `101.1%` 는 "코어 하나를 완전히 점유 중"이라는 뜻입니다.

**MEM 이 0.2% 로 고정**인 점이 중요합니다 — OOM 케이스와 정반대 패턴이고,
이것만으로 "메모리 문제가 아니다"를 배제할 수 있습니다.

### 2-2. 프로그램 실행 로그 — Watchdog 발동 구간 🔄

```
[06:55:15.558] [INFO]     [Worker]   CPU-bound loop started
[06:55:17.562] [INFO]     [Watchdog] cpu=100.3% / max=20%
[06:55:17.562] [CRITICAL] [Watchdog] CPU occupancy exceeded (100.3% >= 20%)
[06:55:17.562] >>> [SYSTEM] WATCHDOG: INITIATING EMERGENCY ABORT (SIGTERM) <<<
```

**`EMERGENCY ABORT` 는 오류 메시지가 아닙니다.** 앱이 정상적으로 작동하는
보호 정책이 **의도대로 실행된 기록**입니다. 이 구분이 리포트의 핵심입니다.

### 2-3. 시스템 도구 출력 — 전체 부하가 아니라 특정 프로세스

```bash
$ ps -eo pid,comm,%cpu,%mem --sort=-%cpu | head -5
    PID COMMAND         %CPU %MEM
   4037 python3         98.4  0.2     ← 범인
      1 tini             0.0  0.0
     12 cron             0.0  0.0
```

```bash
$ ps -L -p 4037 -o pid,tid,%cpu,stat,comm
    PID     TID %CPU STAT COMMAND
   4037    4037 98.4 R    python3     ← 단일 스레드가 전부 점유
```

> **`ps -L` 로 스레드까지 보는 이유:** 한 스레드만 높으면 **단일 루프 과점유**,
> 여러 스레드가 고르게 높으면 **병렬 연산 부하**입니다. 원인이 전혀 다릅니다.
> 여기서는 TID 가 하나뿐이고 `STAT=R`(Running) 이므로 **바쁜 대기(busy-wait)** 입니다.

## 3. Root Cause Analysis (원인 분석)

### 3-1. 현상 분석 — 바쁜 대기(busy-wait)

연산 루프가 **CPU 를 놓아주지 않고** 계속 도는 구조입니다.

```python
while True:
    _ = sum(i * i for i in range(200_000))   # 쉬지 않고 계산
```

`time.sleep()` 이나 I/O 대기가 없으므로, 이 스레드는 **스케줄러가 강제로 뺏기
전까지** CPU 를 계속 씁니다.

### 3-2. CPU 과점유가 시스템 지연을 유발하는 원리

리눅스 기본 스케줄러(CFS)는 **실행 가능한 프로세스들에게 CPU 시간을 공평하게**
나눠줍니다. 여기서 "공평"은 **같은 양**이라는 뜻입니다.

| 상황 | CPU 1개를 나눠 쓰는 모습 |
|---|---|
| 정상 (프로세스 3개) | 각각 33% 씩, 모두 **빠르게 반응** |
| 과점유 1개 발생 | 범인이 쓸 수 있는 만큼 쓰고, 나머지가 **남는 시간을 나눠 가짐** |

**왜 다른 프로세스가 '느려지는'가 — 핵심은 대기 시간입니다.**

1. CPU 는 한 번에 한 작업만 합니다. 여러 프로세스는 **아주 짧게 번갈아** 실행됩니다.
2. 실행 가능한 프로세스가 늘면 **내 차례가 돌아오는 주기가 길어집니다.**
3. 사용자 입장에서는 **"요청을 보냈는데 응답이 늦다"** 로 나타납니다.
   CPU 가 놀고 있는 게 아니라, **내 일이 큐에서 기다리는 중**입니다.
4. 여기에 **컨텍스트 스위칭 비용**이 더해집니다. 프로세스를 바꿀 때마다
   레지스터·캐시를 갈아끼우는데, 전환이 잦아지면 **그 비용 자체가 부하**가 됩니다.
   CPU 사용률은 높은데 실제 처리량은 떨어지는 역설이 생깁니다.

> 그래서 서버 장애 중 "느려졌다"는 신고의 상당수는 **한 프로세스의 과점유**입니다.
> 전체 CPU 만 보면 "서버가 바쁘다"까지만 알 수 있고,
> **프로세스별로 봐야 "누가 바쁘게 만들었나"** 를 답할 수 있습니다.
> `monitor.sh` 를 특정 프로세스 기준으로 만든 이유가 이것입니다.

### 3-3. Watchdog 정책의 동작 원리

Watchdog(감시견)은 **"정해진 범위를 벗어나면 개입한다"** 는 패턴입니다.
하드웨어 워치독 타이머에서 온 이름으로, 일정 시간 안에 신호가 오지 않으면
시스템을 리셋하는 장치였습니다.

이 앱의 Watchdog 은 주기적으로 자기 CPU 사용률을 재고,
`CPU_MAX_OCCUPY` 를 넘으면 **SIGTERM 으로 자신을 종료**시킵니다.

**왜 SIGKILL 이 아니라 SIGTERM 인가:**

| 신호 | 번호 | 성격 | 앱이 할 수 있는 일 |
|---|---|---|---|
| `SIGTERM` | 15 | 종료 **요청** | 파일 닫기, 로그 남기기, 연결 정리 **가능** |
| `SIGKILL` | 9 | 즉시 종료 | **아무것도 못 함** (커널이 직접 처리) |

CPU 과점유는 **데이터가 깨질 위험이 적어서** 정리할 시간을 줍니다.
반면 메모리 고갈은 **지금 당장 멈춰야** 시스템이 사니까 SIGKILL 입니다.

## 4. Workaround & Verification (조치 및 검증)

### 4-1. 조치 내용

환경변수 `CPU_MAX_OCCUPY` 를 단계적으로 상향하며 생존 시간을 측정했습니다.

### 4-2. Before & After 🔄

| `CPU_MAX_OCCUPY` | 생존 시간 | 종료 시점 측정값 |
|---:|---:|---|
| **20%** (Before) | **8초** | `cpu=22.4%` |
| 50% | 21초 | `cpu=52.7%` |
| **90%** (After) | **36초** | `cpu=93.6%` |

```
CPU_MAX_OCCUPY=20  → 생존  8초, 종료 시점 cpu=22.4%
CPU_MAX_OCCUPY=50  → 생존 21초, 종료 시점 cpu=52.7%
CPU_MAX_OCCUPY=90  → 생존 36초, 종료 시점 cpu=93.6%
```

**임계값과 생존 시간이 거의 선형 관계**입니다. 부하가 시간에 따라 점진적으로
오르는 구조이므로, 임계값을 올리면 **그 지점에 도달할 때까지의 시간만큼** 더 삽니다.

> **종료 시점의 측정값이 임계값을 '살짝' 넘는 것**(22.4 vs 20, 52.7 vs 50)도
> 의미가 있습니다. 2초 간격으로 점검하므로 **점검과 점검 사이에 넘어선 분량**입니다.
> 점검 주기가 길수록 이 초과폭이 커집니다.

### 4-3. 검증 결과 해석

> **임계값 상향은 "경고를 끄는 것"에 가깝습니다.**
> CPU 를 100% 쓰는 동작 자체는 **전혀 바뀌지 않았습니다.**
> 오히려 임계값을 올릴수록 **다른 프로세스가 피해를 보는 시간이 길어집니다.**
>
> OOM 케이스가 "터지는 시점을 미룬 것"이라면,
> 이쪽은 **"터지는 걸 막던 안전장치를 느슨하게 한 것"** 이라 더 위험합니다.

### 4-4. 근본적 해결 제안

| 우선순위 | 제안 | 설명 |
|---|---|---|
| 1 | **바쁜 대기 제거** | 루프에 `time.sleep()` 을 넣거나, 이벤트 기반으로 전환해 **CPU 를 놓아준다** |
| 2 | **알고리즘 개선** | 같은 계산을 반복한다면 **캐싱**. O(n²) 루프라면 자료구조 재검토 |
| 3 | **cgroup 으로 상한** | `cpu.max` 로 **커널 차원에서** 제한. 앱이 폭주해도 다른 프로세스를 지킬 수 있다 |
| 4 | **nice 값 조정** | 우선순위를 낮춰(`nice -n 19`) 다른 프로세스에 양보 |

> 3번이 특히 중요합니다. 앱의 Watchdog 은 **앱이 정상일 때만** 작동합니다.
> 앱 자체가 망가지면 안 돌아갑니다. **cgroup 은 커널이 강제**하므로 더 믿을 수 있습니다.

### 4-5. 재현 방법

```bash
./run.sh case cpu 20     # Before — 8초 만에 종료
./run.sh case cpu 90     # After  — 36초 생존
./run.sh diagnose cpu    # ps -L 스레드별 CPU 포함 증거 수집
```
