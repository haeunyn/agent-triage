# [Bug] CPU Spike - 과점유 방지 정책(Watchdog)에 의한 프로세스 강제 종료

> **증거 데이터 출처**
> 코디세이 제공 바이너리 `agent-leak-app-arm64` 를 직접 실행해 얻은 실측값입니다.
> 측정 일시 **2026-11-07 09:25~09:37 (KST)**, 환경 Docker `agent-triage` (Ubuntu, aarch64, 8코어).
> 재현 명령은 **4-3절**에 적었습니다.

---

## 1. Description (현상 설명)

`CPU_MAX_OCCUPY` 를 51 이상으로 두고 `agent-leak-app` 을 실행하면,
앱이 보고하는 부하가 서서히 오르다가 50% 를 넘는 순간 이 로그를 냅니다.

```
[CRITICAL] [CpuWorker] CPU Threshold Violated! (52.48%).
```

| 항목 | 내용 |
|---|---|
| **조건** | `CPU_MAX_OCCUPY ≥ 51` · `MEMORY_LIMIT=512` · `MULTI_THREAD_ENABLE=false` |
| **언제** | 기동 후 **약 30~90초** (임계값이 높을수록 늦게 — 부하가 점진 상승) |
| **위반 수치** | 측정 4회 모두 **50% 를 갓 넘긴 값** — 50.93 / 51.00 / 52.48 / 53.29 / 55.85% |
| **메모리** | 0.4~0.5% 로 **변화 없음** → 메모리와 무관 |

### ⚠️ 가장 중요한 발견 — 앱이 보고하는 부하는 '실제 CPU 점유'가 아닙니다

앱 로그가 `Current Load: 55.85%` 라고 찍는 동안, **OS 로 재 본 실제 CPU 사용량은
0.5% 미만**이었습니다. 세 가지 방법으로 각각 확인했습니다.

| 측정 방법 | 결과 | 같은 시점 앱 보고 |
|---|---|---|
| `monitor.sh` (프로세스 트리, 1초 창) | **0.0 ~ 3.9%** | 8.73 → 53.29% |
| `/proc/<pid>/stat` 틱 누적 (5초 창 6회) | **0.0 / 0.0 / 0.0 / 0.2 / 0.0 / 0.2%** | 22.09 → 38.33% |
| `/proc/stat` 시스템 전체 (4초 창 6회) | **0.2 ~ 0.5%** | 13.85 → 55.85% |

**즉 이 앱은 CPU 를 실제로 태우지 않습니다.** 올라가는 숫자를 스스로 만들어 보고하고,
그 숫자가 50% 를 넘으면 자기 임계 위반을 선언합니다.

> **이게 진단에서 왜 중요한가.**
> 앱이 "CPU 55%" 라고 말하는데 `top`·`ps`·`/proc` 은 0% 라고 말합니다. 둘 중
> **OS 를 믿어야 합니다.** 애플리케이션이 보고하는 수치는 그 앱이 자기 기준으로
> 계산한 값이고, 버그가 있거나 단위가 다르거나 아예 합성된 값일 수 있습니다.
> **"앱 텔레메트리와 OS 관측이 어긋나면 교차 검증한다"** 가 이 케이스의 교훈입니다.
>
> 실제 장애 대응에서도 같은 일이 자주 생깁니다. APM 대시보드는 빨간데 서버는
> 한가하거나, 그 반대이거나. 어느 쪽이 거짓인지 가리는 것이 진단의 첫 단계입니다.

## 3. Root Cause Analysis (원인 분석)

### 3-1. 현상 분석 — 실제 과점유가 아니라 '보고값 이상'

> **먼저 밝혀둘 것.** 제공 바이너리는 `stripped` 실행 파일이고, 과제 제약에
> **「바이너리 디컴파일 및 리버스 엔지니어링 시도 금지」** 가 있습니다.
> 아래는 **밖에서 관찰한 사실과 그로부터의 추론**입니다.

**관찰된 사실**

| 사실 | 근거 |
|---|---|
| 앱 보고 부하가 3초마다 단조 상승 | 2-2 앱 로그 |
| 실제 CPU 점유는 0.5% 미만 | 1절 세 가지 측정 |
| 50% 를 넘으면 `CPU Threshold Violated!` | 2-2, 4-2 |
| 50 이하로 설정하면 정점에서 쿨다운 후 하강 | 4-2 |

**추론**: `CpuWorker` 는 실제 연산 부하를 만드는 대신 **부하 수치를 합성해
올리고 내리는 시뮬레이터**로 동작합니다. 장애 진단 연습용 교보재이므로
평가자 PC 를 실제로 느리게 만들지 않도록 이렇게 만든 것으로 보입니다.

#### 진짜 바쁜 대기(busy-wait)는 어떤 모습인가

참고로, **실제로** CPU 를 과점유하는 코드는 이런 구조입니다.
아래는 바이너리의 소스가 아니라 **같은 증상을 만드는 전형적 패턴**이며,
진단 연습용으로 직접 작성한 `sim/fault_sim.py` 가 이 구조입니다.

```python
while True:
    _ = sum(i * i for i in range(200_000))   # 쉬지 않고 계산
```

`time.sleep()` 이나 I/O 대기가 없으므로, 이 스레드는 **스케줄러가 강제로 뺏기
전까지** CPU 를 계속 씁니다. 이 경우 `ps` 의 `%CPU` 가 코어 하나를 꽉 채운
100% 근처로 찍히고 `STAT` 이 `R`(Running) 로 보입니다 — **제공 바이너리에서는
그런 값이 한 번도 관측되지 않았습니다.**

### 3-2. CPU 과점유가 시스템 지연을 유발하는 원리

리눅스 기본 스케줄러(CFS)는 **실행 가능한 프로세스들에게 CPU 시간을 공평하게**
나눠줍니다. 여기서 "공평"은 **같은 양**이라는 뜻입니다.

| 상황 | CPU 1개를 나눠 쓰는 모습 |
|---|---|
| 정상 (프로세스 3개) | 각각 33% 씩, 모두 **빠르게 반응** |
| 과점유 1개 발생 | 범인이 쓸 수 있는 만큼 쓰고, 나머지가 **남는 시간을 나눠 가짐** |

**왜 다른 프로세스가 '느려지는'가 — 핵심은 대기 시간입니다.**

1. CPU 는 한 번에 한 작업만 합니다. 여러 프로세스는 **아주 짧게 번갈아** 실행됩니다.
2. 실행 가능한 프로세스가 늘면 **내 차례가 돌아오는 주기가 길어집니다.**
3. 사용자 입장에서는 **"요청을 보냈는데 응답이 늦다"** 로 나타납니다.
   CPU 가 놀고 있는 게 아니라, **내 일이 큐에서 기다리는 중**입니다.
4. 여기에 **컨텍스트 스위칭 비용**이 더해집니다. 프로세스를 바꿀 때마다
   레지스터·캐시를 갈아끼우는데, 전환이 잦아지면 **그 비용 자체가 부하**가 됩니다.
   CPU 사용률은 높은데 실제 처리량은 떨어지는 역설이 생깁니다.

> 그래서 서버 장애 중 "느려졌다"는 신고의 상당수는 **한 프로세스의 과점유**입니다.
> 전체 CPU 만 보면 "서버가 바쁘다"까지만 알 수 있고,
> **프로세스별로 봐야 "누가 바쁘게 만들었나"** 를 답할 수 있습니다.
> `monitor.sh` 를 특정 프로세스 기준으로 만든 이유가 이것입니다.

### 3-3. Watchdog 정책의 동작 원리

Watchdog(감시견)은 **"정해진 범위를 벗어나면 개입한다"** 는 패턴입니다.
하드웨어 워치독 타이머에서 온 이름으로, 일정 시간 안에 신호가 오지 않으면
시스템을 리셋하는 장치였습니다.

이 앱의 `CpuWorker` 는 주기적으로 **자기가 계산한 부하값**을 점검하고,
50% 를 넘으면 `[CRITICAL] CPU Threshold Violated!` 를 남깁니다.

**다만 OOM 케이스와 달리 종료 신호가 관측되지 않았습니다.**
리포트 01 의 메모리 가드는 `Self-terminating process <pid>` 를 명시적으로 찍고
즉시 사라졌지만, CPU 임계 위반 뒤의 거동은 일정하지 않았습니다.

| 관측 | 위반 이후 |
|---|---|
| 1회차 (`CPU_MAX_OCCUPY=90`, 2-1 로그) | 약 2초 뒤 프로세스 소멸 (`STATE:NOT_RUNNING`) |
| 2회차 (`=90`, 15초 추적) | **15초 뒤까지 생존** — 다만 그 뒤 `CpuWorker` 로그가 멈춤 |
| 3회차 (`=51`, `=60`) | 위반 로그 1줄만 남고 생존 |

**그래서 "CPU 위반 시 SIGTERM 으로 종료된다"고 단정하지 않았습니다.**
측정값이 일정하지 않으면 단정하지 않는 것이 맞습니다.
확실한 것은 **① 50% 초과 시 CRITICAL 을 남긴다 ② 그 뒤 워커가 일을 멈춘다** 입니다.

#### 참고 — SIGTERM 과 SIGKILL 의 차이 (일반 지식)

리포트 01 의 메모리 가드처럼 **프로세스를 종료시키는 보호 정책**을 설명할 때
반드시 나오는 구분이라 정리해 둡니다.

| 신호 | 번호 | 성격 | 앱이 할 수 있는 일 |
|---|---|---|---|
| `SIGTERM` | 15 | 종료 **요청** | 파일 닫기, 로그 남기기, 연결 정리 **가능** |
| `SIGKILL` | 9 | 즉시 종료 | **아무것도 못 함** (커널이 직접 처리) |

일반적으로 CPU 과점유는 **데이터가 깨질 위험이 적어서** 정리할 시간을 주고,
메모리 고갈은 **지금 당장 멈춰야** 시스템이 사니까 즉시 종료시킵니다.
(이 앱에서 실제로 어느 신호가 쓰였는지는 위에 적은 대로 **확인되지 않았습니다.**)

## 4. Workaround & Verification (조치 및 검증)

### 4-1. 조치 내용

`CPU_MAX_OCCUPY` 를 **50 이하**로 설정합니다.

```bash
export CPU_MAX_OCCUPY=20     # 부트 6단계에서 [ OK ] 로 통과하는 값
```

### 4-2. Before & After — 경계는 50 과 51 사이입니다

값을 바꿔가며 측정했습니다 (`MEMORY_LIMIT=512`, `MULTI_THREAD_ENABLE=false` 고정).

| `CPU_MAX_OCCUPY` | 정점에서 일어난 일 | 결과 |
|---:|---|---|
| **20** | `Peak reached (20.00%). Starting cooldown...` | **정상** — 쿨다운 후 재상승 |
| **50** | `Peak reached (50.00%). Starting cooldown...` | **정상** |
| **51** | `Peak reached (51.00%)` → `[CRITICAL] Threshold Violated! (51%)` | **위반** |
| **60** | `[CRITICAL] Threshold Violated! (53.02%)` | **위반** |
| **90** | `[CRITICAL] Threshold Violated! (52.48 / 53.29 / 55.85%)` | **위반** |

**위반 판정 기준은 `CPU_MAX_OCCUPY` 가 아니라 고정된 50% 입니다.**
설정을 90 으로 줘도 위반은 **53% 대에서** 선언됐습니다. 즉 `CPU_MAX_OCCUPY` 는
"워커가 어디까지 부하를 올릴 것인가"(목표치)이고, 위반선은 그와 별개로 50% 에
고정돼 있습니다. **목표치를 50 보다 높게 주면 가는 길에 반드시 위반선을 밟습니다.**

> 리포트 초안에는 "임계값과 생존 시간이 선형 관계"라고 적혀 있었는데
> **실측에서 틀렸습니다.** 50 이하면 아예 위반하지 않고 무한히 돌고,
> 51 이상이면 위반합니다. 선형이 아니라 **계단**입니다.

#### Before (`=90`) / After (`=20`) 비교

| | Before (`=90`) | After (`=20`) |
|---|---|---|
| 관제 샘플 | 10개 + `NOT_RUNNING` | **20개, 전부 정상** |
| 보고 부하 | 8.73 → 53.29% **단조 상승** | 20.00% 찍고 **하강** (10.85 → 6.26) |
| 마지막 로그 | `[CRITICAL] CPU Threshold Violated!` | `Peak reached (20.00%). Starting cooldown...` |
| 실제 CPU | 0 ~ 3.9% | 0 ~ 4.9% — **차이 없음** |

**실제 CPU 사용량은 Before·After 가 사실상 같습니다.** 달라진 것은
앱이 자기 부하를 어디까지 올리다 멈추는지, 그리고 위반을 선언하는지 여부뿐입니다.
**이것이 "실제 과점유 장애가 아니다"의 가장 직접적인 근거입니다.**

### 4-3. 재현 방법

```bash
./run.sh up
./run.sh case cpu 90     # Before — 임계 위반
./run.sh case cpu 20     # After  — 정상 쿨다운
./run.sh diagnose cpu
```

> `run.sh` 의 `case cpu` 는 `MEMORY_LIMIT=512` 와 `MULTI_THREAD_ENABLE=false` 를
> **함께 고정**합니다. 그러지 않으면 메모리 가드나 교착이 먼저 터져서
> CPU 거동을 볼 수 없습니다 — 처음에 이것 때문에 CPU 20·50·90 의
> 생존 시간이 전부 같게 나왔습니다 (`과제4-2_평가준비/00_시작하기.md` 참고).

### 4-4. 근본적 해결 제안

| 우선순위 | 제안 | 설명 |
|---|---|---|
| 1 | **부하 측정값 교차 검증** | 앱이 보고하는 수치를 `/proc` 기준 실측과 비교. 어긋나면 앱의 측정 로직을 의심한다 |
| 2 | **임계값을 설정과 일치시키기** | 위반선이 50% 로 고정돼 있어 `CPU_MAX_OCCUPY=90` 설정이 무의미하다. 설정값이 실제로 쓰이게 해야 한다 |
| 3 | **busy-wait 라면 양보 추가** | 실제 연산 루프라면 `time.sleep(0)` / `os.sched_yield()` 로 CPU 를 놓아준다 |
| 4 | **관제 기준을 OS 지표로** | 앱 자체 보고가 아니라 `monitor.sh` 처럼 OS 가 보는 값으로 경보를 걸어야 거짓 경보를 막는다 |
