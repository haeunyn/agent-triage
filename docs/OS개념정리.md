# OS 개념 정리 — 이 미션이 요구하는 4가지

> 과제 3절 "미션 목표"가 설명을 요구하는 항목들입니다.

## 1. 메모리 구조와 누수의 영향

프로세스 메모리는 네 구역입니다.

| 구역 | 담는 것 | 크기 |
|---|---|---|
| 코드(Text) | 실행 명령 | 고정 |
| 데이터(Data/BSS) | 전역·정적 변수 | 고정 |
| **힙(Heap)** | 실행 중 동적 할당 | **위로 자람 ← 누수 발생 지점** |
| 스택(Stack) | 지역 변수·호출 정보 | 아래로 자람 |

**누수가 시스템 전체로 번지는 경로:**

```
힙 계속 증가 → 물리 메모리 부족 → 스왑 시작(디스크, 수만 배 느림)
            → 스래싱(CPU 가 메모리 옮기는 데만 소모)
            → 범인이 아닌 프로세스까지 전부 느려짐
            → OOM Killer 작동 (범인을 고른다는 보장 없음)
```

**GC 가 있어도 누수는 생깁니다.** GC 는 "아무도 참조하지 않는 객체"만 치웁니다.
리스트가 붙잡고 있으면 **살아 있는 것으로 간주**되어 회수되지 않습니다.

- `VmRSS` = 실제 물리 메모리 점유 ← **누수 추적은 이 값**
- `VmSize` = 가상 주소 공간 (예약만 한 것 포함, 늘 큼)
- `MemFree` 가 아니라 **`MemAvailable`** 을 봐야 함 (캐시는 필요하면 비워짐)

## 2. CPU 과점유가 지연을 유발하는 원리

리눅스 CFS 스케줄러는 실행 가능한 프로세스에게 CPU 시간을 **공평하게** 나눕니다.

1. CPU 는 한 번에 하나만 처리 → 여러 프로세스가 **아주 짧게 번갈아** 실행
2. 실행 가능한 프로세스가 늘면 **내 차례 주기가 길어짐**
3. 사용자에겐 "응답이 늦다"로 보임 — CPU 가 노는 게 아니라 **큐에서 대기 중**
4. **컨텍스트 스위칭 비용**이 더해짐 → 사용률은 높은데 처리량은 떨어지는 역설

> **프로세스별로 봐야 범인을 찾습니다.** 전체 CPU 만 보면 "서버가 바쁘다"까지만 압니다.

- 리눅스에서 **코어 1개 = 100%**. 4코어면 한 프로세스가 400% 까지 가능
- `ps` 의 `%CPU` 는 **수명 전체 평균** → 급상승 구간을 놓침.
  `/proc/<pid>/stat` 을 두 번 읽어 **차이**를 봐야 함
- `ps -L` 로 스레드별 확인: 한 스레드만 높으면 단일 루프, 고르게 높으면 병렬 부하

## 3. 교착상태(Deadlock)

**둘 이상의 스레드가 서로가 가진 자원을 기다려 모두 영원히 멈춘 상태.**

### 4대 조건 — 넷이 동시에 성립해야만 발생

| 조건 | 뜻 | 깨는 방법 |
|---|---|---|
| 상호 배제 | 자원은 한 번에 하나만 | 락 합치기 / 불변 자료구조 |
| 점유 대기 | 쥔 채로 다른 걸 기다림 | **타임아웃** 후 가진 것 반납 |
| 비선점 | 강제로 뺏을 수 없음 | (OS 레벨 — 앱에서 바꾸기 어려움) |
| **순환 대기** | 대기가 고리를 이룸 | ★ **락 순서 통일** (가장 현실적) |

### 시스템 도구로 식별하는 법

| 증거 | 명령 | 봐야 할 것 |
|---|---|---|
| 죽지 않음 | `ps -ef \| grep` | PID 존재 |
| 일하지 않음 | `ps -p <pid> -o stat` | **`S`**(대기), `R` 아님 |
| **무엇을 기다리나** | `ps -L -o wchan` | **`futex_wait`** = 락 대기 |
| 정체 | `ps -o %cpu,%mem` 반복 | 값이 안 변함 |
| 멈춘 지점 | 앱 로그 `tail` | `WAITING ... BLOCKED` |

> **가장 발견하기 어려운 장애입니다.** PID 살아 있고, 포트 LISTEN 유지되고,
> CPU/MEM 낮고 안정적 — **모든 지표가 정상으로 보입니다.**
> Health Check 만으로는 못 잡고 **무응답 감지**가 따로 필요합니다.

## 4. 장애 리포트로 소통하기

| | 나쁜 예 | 좋은 예 |
|---|---|---|
| 현상 | "자꾸 죽어요" | "실행 후 약 23초 뒤 `SELF-TERMINATED` 남기고 종료" |
| 증거 | "메모리가 많이 찼어요" | `MEM:1.0% → 6.3%` 8개 샘플 + 로그 3줄 |
| 원인 | "누수인 것 같아요" | "참조 유지로 GC 대상 제외 → MemoryGuard 가 SIGKILL" |
| 조치 | "설정 바꿨더니 됐어요" | "256→512MB, 23초→49초. **단 근본 해결은 아님**" |

**핵심은 육하원칙 + 재현 가능성.** 읽는 사람이 같은 절차로 같은 결과를 얻어야 합니다.

## 부록 — 종료 신호 읽는 법

| 종료 코드 | 신호 | 의미 | 이 미션에서 |
|---|---|---|---|
| 137 | SIGKILL(9) | **즉시 중단**, 앱이 아무것도 못 함 | **OOM** — 당장 멈춰야 시스템이 산다 |
| 143 | SIGTERM(15) | 종료 **요청**, 정리할 시간 있음 | **CPU** — 데이터 깨질 위험 적음 |
| (없음) | — | 살아 있으나 무응답 | **Deadlock** |

> `128 + 신호번호` 가 종료 코드입니다. **종료 코드만 봐도 어느 정책이 작동했는지** 압니다.
