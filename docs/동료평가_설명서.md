# 항목 2 — 방법 설명 (말로 한다)

## 2-1. `monitor.sh` 에서 메모리 증가 패턴을 추적한 명령어와 데이터 추출 방법

**② 실행**
```bash
./run.sh shell
grep -n "VmRSS\|status" /opt/agent-triage/bin/monitor.sh | head
```

**④ 설명할 말**

> *"`/proc/<PID>/status` 를 읽어서 **`VmRSS`** 한 줄만 꺼냈습니다. `awk` 로 숫자 필드만 뽑아 KB 단위로 받고, 이걸 일정 간격으로 반복해 **시간-메모리 쌍**을 로그에 남겼습니다. 그래서 '선형으로 올라간다'가 눈으로 보입니다."*
>
> *"**`VmSize` 가 아니라 `VmRSS` 를 쓴 이유**가 있습니다. `VmSize` 는 '주소 공간을 얼마나 예약했나'라서 실제로 안 쓰는 영역까지 포함됩니다. **`VmRSS` 는 지금 물리 메모리를 실제로 몇 KB 쓰고 있나**입니다. OOM 은 물리 메모리가 모자라서 나는 거라 `VmRSS` 가 맞습니다."*

**꼬리 질문 — "`ps` 로도 되지 않나요?"**
> *"됩니다. 다만 `ps` 는 매번 프로세스를 새로 띄우는 비용이 있고 출력 형식이 OS 마다 다릅니다. `/proc` 은 **파일을 읽는 것**이라 가볍고 형식이 고정입니다. 매분 도는 관제 스크립트에는 `/proc` 쪽이 맞다고 봤습니다."*

## 2-2. CPU 사용률 확인에 선택한 도구와 옵션의 의미

**④ 설명할 말**

> *"`ps` 를 **`-L` 옵션**과 함께 썼습니다. `-L` 은 **스레드 단위**로 보여줍니다. 프로세스 전체 CPU 가 100% 로 보여도, 그게 **한 스레드가 다 먹는 것인지 여러 스레드가 나눠 쓰는 것인지**는 `-L` 없이는 구분이 안 됩니다. CPU Spike 장애는 특정 워커 스레드 하나가 도는 것이라 스레드별로 봐야 했습니다."*
>
> *"`top` 은 화면을 계속 새로 그려서 **로그로 남기기 어렵습니다.** 한 번 찍어서 파일에 남기는 용도로는 `ps` 가 낫습니다."*

**꼬리 질문 — "`%CPU` 는 무엇에 대한 비율인가요?"**
> *"`ps` 의 `%CPU` 는 **프로세스가 살아 있는 동안의 평균**입니다. 방금 1초 동안의 값이 아닙니다. 그래서 '지금 치솟았는지'를 보려면 **두 번 찍어서 차이를 봐야** 합니다. 저는 `/proc/stat` 을 **두 번 읽어 차이를 내는** 방식도 같이 썼습니다."*

## 2-3. "살아있지만 멈춰있는 상태" 진단 — 도구와 순서, 판단 흐름 ★

**② 실행**
```bash
./run.sh case deadlock     # 교착 재현
./run.sh diagnose          # 진단 스크립트
```

**④ 설명할 말 — 순서대로 말하는 것이 핵심이다**

> *"**네 단계로 좁혔습니다.**"*
>
> *"**① 살아 있나** — `ps` 로 PID 가 있는지 봤습니다. **있었습니다.** 그래서 죽은 게 아닙니다."*
>
> *"**② 일을 하고 있나** — CPU 와 메모리를 두 번 찍어 비교했습니다. **둘 다 변화가 없었습니다.** 살아는 있는데 아무 일도 안 한다는 뜻입니다."*
>
> *"**③ 로그가 멈췄나** — 앱 로그의 마지막 타임스탬프를 봤습니다. **특정 시각 이후로 한 줄도 안 늘었습니다.** 여기서 '멈춘 것'이 확정됐습니다."*
>
> *"**④ 왜 멈췄나** — `/proc/<PID>/task/*/wchan` 을 읽었습니다. 커널이 **이 스레드가 무엇을 기다리는 중인지** 적어두는 곳입니다. **`futex`** 가 나왔습니다. futex 는 락을 기다릴 때 쓰는 커널 기능이라, **서로 락을 기다리는 교착**이라고 판단했습니다."*
>
> *"요약하면 **살아있나 → 일하나 → 로그가 도나 → 무엇을 기다리나** 순으로, 매 단계에서 가능성을 하나씩 지웠습니다."*

# 항목 3 — 원리 설명 (말로 한다. 가장 많이 물어본다)

## 3-1. 메모리 누수 시 애플리케이션의 메모리 보호 정책이 강제 종료하는 이유

**⚠️ 이 문항은 단어를 정확히 써야 한다. "OOM Killer" 가 아니다.**

> *"이 앱은 **스스로** 죽습니다. 리눅스 커널의 OOM Killer 가 죽인 게 아닙니다."*
>
> *"앱 안에 **MemoryGuard** 라는 자체 감시 기능이 있어서, 자기 사용량이 `MEMORY_LIMIT` 을 넘으면 **자진 종료**합니다. 로그에도 그렇게 찍힙니다."*
>
> *"**왜 그렇게 만드나** — 커널 OOM Killer 한테 맡기면 두 가지가 나쁩니다. 첫째, **언제 죽을지 모릅니다.** 시스템 전체가 한계에 다다라야 작동합니다. 둘째, **누가 죽을지 모릅니다.** OOM Killer 는 점수를 매겨 고르기 때문에 **애먼 다른 프로세스**가 죽을 수 있습니다."*
>
> *"스스로 한도를 정해 먼저 죽으면 **죽는 시점과 대상이 예측 가능**해지고, **로그를 남기고 정리하고 죽을 수 있습니다.** 그래서 서버 프로그램들이 자체 한도를 두는 겁니다."*

**꼬리 질문 — "그럼 OOM Killer 는 언제 나오나요?"**
> *"자체 한도가 없거나 한도보다 먼저 시스템 전체 메모리가 바닥났을 때입니다. 그 전에 보통 **스왑** 을 쓰기 시작하는데, 스왑은 디스크라서 수천 배 느립니다. 그래서 **죽기 전에 먼저 엄청나게 느려지는** 구간이 생깁니다. 이걸 **스래싱**이라고 합니다."*

## 3-2. CPU 과점유 시 단일 프로세스를 종료하는 것이 시스템 보호에 왜 필요한가

> *"CPU 는 **나눠 쓰는 자원**입니다. 한 프로세스가 계속 점유하면 다른 프로세스들이 **차례를 못 받습니다.** 그러면 SSH 접속도 느려지고, 관제 스크립트도 못 돌고, **고치러 들어갈 수조차 없는 상태**가 됩니다."*
>
> *"**하나를 죽이는 게 전체를 지키는 선택**입니다. 장애 하나를 장애 전체로 번지지 않게 막는 겁니다. 실제로 이 미션에서도 CPU 를 90으로 올리니 다른 명령 응답이 눈에 띄게 느려졌습니다."*

## 3-3. 교착 상태를 "상호 배제"와 "순환 대기"로 설명 ★

**⚠️ 평가표가 두 단어를 콕 집었다. 그 단어를 반드시 입에 올려야 한다.**

> *"교착은 네 조건이 동시에 맞아야 생기는데, 평가표가 물은 두 가지가 핵심입니다."*
>
> *"**상호 배제(Mutual Exclusion)** — 한 자원은 **한 번에 한 스레드만** 쓸 수 있다는 뜻입니다. 락이 그래서 있습니다. 공유하면 데이터가 깨지니까요. 그런데 이 성질 때문에 **기다림이 생깁니다.**"*
>
> *"**순환 대기(Circular Wait)** — 기다림이 **고리**를 이루는 상태입니다. A 는 B 가 가진 락을 기다리고, B 는 A 가 가진 락을 기다립니다. 둘 다 상대가 놓기를 기다리는데 **둘 다 놓지 않습니다.** 영원히 멈춥니다."*
>
> *"나머지 두 조건은 **점유 대기**(가진 채로 기다림)와 **비선점**(뺏을 수 없음)입니다. 네 개 중 **하나만 깨도 교착은 안 생깁니다.** 그래서 보통 **락을 항상 같은 순서로 잡게** 해서 순환 대기를 없앱니다."*

## 3-4. 로그에서 스레드 간 순환 의존(A→B, B→A)을 어떻게 파악했는지

> *"앱 로그에 **어느 스레드가 어느 락을 잡았고 무엇을 기다리는지**가 찍힙니다. 마지막 몇 줄을 보니 **Worker-A 가 Lock-2 를 기다리고, Worker-B 가 Lock-1 을 기다리는 상태**에서 멈춰 있었습니다."*
>
> *"그 직전 줄을 거슬러 보니 **A 는 Lock-1 을 이미 쥐고 있었고, B 는 Lock-2 를 쥐고 있었습니다.** 즉 A 는 B 의 것을, B 는 A 의 것을 기다립니다. **고리가 닫혔습니다.**"*
>
> *"로그만으로 확신하기 어려워서 `/proc/<PID>/task/*/wchan` 으로 **커널이 보는 대기 상태**도 확인했습니다. `futex` 가 나와서 락 대기가 맞다고 교차 검증했습니다."*

# 항목 4 — 확장 질문 (정답 없음. 근거를 대면 된다)

## 4-1. 운영 서버였다면 장애 전에 탐지하도록 `monitor.sh` 를 어떻게 개선하겠는가

> *"지금은 **한도를 넘었을 때** 경고합니다. 운영이라면 **넘기 전에** 알아야 합니다. 세 가지를 넣겠습니다."*
>
> *"**① 기울기를 본다** — 값 하나가 아니라 **최근 N회의 증가 추세**를 봅니다. 10분마다 10MB씩 꾸준히 는다면, 한도까지 몇 시간 남았는지 계산할 수 있습니다. **'2시간 뒤 한계'** 를 미리 알리는 게 진짜 예방입니다."*
>
> *"**② 재시작해도 기억한다** — 지금은 프로세스가 죽으면 기록이 끊깁니다. 로그를 **시계열로 쌓아** 어제와 오늘을 비교할 수 있게 합니다. 누수는 **며칠에 걸쳐** 드러나는 경우가 많습니다."*
>
> *"**③ 알림을 등급으로 나눈다** — 지금은 종료 코드 0/1/2 로만 구분합니다. **주의(추세 이상) / 경고(80% 도달) / 장애(종료)** 로 나눠야 진짜 장애가 묻히지 않습니다."*

## 4-2. OOM · CPU Spike · Deadlock 중 실제 서비스에서 가장 치명적인 것 ★

**고르고 근거를 대면 된다. 아래는 하나의 답이고, 다르게 골라도 된다.**

> *"**Deadlock 이 가장 치명적**이라고 봅니다."*
>
> *"**이유는 '죽지 않기 때문'입니다.** OOM 과 CPU Spike 는 프로세스가 **죽습니다.** 죽으면 감시 도구가 알아채고, 재시작이 걸리고, 알림이 갑니다. **대응이 자동으로 시작됩니다.**"*
>
> *"Deadlock 은 **PID 가 살아 있습니다.** 헬스체크가 '프로세스 있음'만 보면 **정상으로 보고합니다.** 포트도 열려 있어서 로드밸런서가 계속 트래픽을 보냅니다. **요청이 쌓이기만 하고 아무도 모릅니다.** 사람이 '이상하게 느리다'고 신고할 때까지 갑니다."*
>
> *"**근본 예방**은 두 가지입니다. **① 락 순서를 전역으로 고정**해서 순환 대기를 구조적으로 없애는 것, **② 락에 타임아웃을 두어** 일정 시간 못 잡으면 실패로 돌려보내는 것입니다. 타임아웃은 교착을 막지는 못해도 **영원히 멈추는 것은 막습니다.**"*
>
> *"그리고 **헬스체크를 '프로세스 있음'이 아니라 '실제로 응답함'으로** 바꿔야 합니다. 이번 미션에서 제가 로그 타임스탬프를 본 것과 같은 이유입니다."*

## 4-3. OOM 과 Deadlock 이 동시에 발생했다면 어떤 순서로? 우선순위 근거는?

> *"**OOM 을 먼저** 봅니다."*
>
> *"**근거 ① 측정이 안 됩니다.** 메모리가 모자라면 시스템이 스왑을 쓰기 시작해서 **모든 것이 느려집니다.** 그 상태에서는 '이 스레드가 멈춘 것'인지 '느린 것'인지 구분이 안 됩니다. **교착 진단 자체가 불가능**해집니다."*
>
> *"**근거 ② 범위가 다릅니다.** OOM 은 **시스템 전체**에 영향을 주고, 다른 프로세스까지 죽을 수 있습니다. 교착은 보통 **그 프로세스 안**의 문제입니다. **넓게 퍼지는 것부터** 막는 게 맞습니다."*
>
> *"**근거 ③ 인과 관계일 수 있습니다.** 메모리가 부족해 할당이 지연되면서 락 보유 시간이 길어져 교착이 **유발됐을 수도** 있습니다. 그러면 OOM 을 고치는 것만으로 교착이 사라집니다. **원인이 결과보다 먼저**입니다."*

## 4-4. 소스를 직접 고칠 수 있다면 장애 유형별 코드 레벨 개선

> *"환경변수 조정은 **증상을 가린 것**이지 고친 게 아닙니다. 리포트에도 그렇게 적었습니다."*
>
> | 장애 | 코드 레벨 개선 |
> |---|---|
> | **OOM** | 누수 지점을 찾아 **참조를 끊습니다.** 캐시라면 **최대 크기와 만료**를 둡니다. 무한히 쌓이는 리스트를 **크기 제한 큐**로 바꿉니다 |
> | **CPU** | 바쁜 대기(busy-wait) 루프를 **이벤트 대기**로 바꿉니다. 무거운 작업은 **배치·샘플링**으로 줄입니다 |
> | **Deadlock** | **락 획득 순서를 전역으로 고정**합니다. 락 범위를 최소로 줄이고, 가능하면 **락 없는 구조**(메시지 큐)로 바꿉니다 |
>
> *"공통으로 **테스트를 추가**하겠습니다. 누수는 **장시간 실행 테스트**, 교착은 **동시성 스트레스 테스트**로 잡힙니다."*

## 4-5. 다시 한다면 어떤 점을 다르게 하겠는가

> *"**장애를 하나씩 분리하는 작업을 먼저** 하겠습니다."*
>
> *"처음에 `CPU_MAX_OCCUPY` 만 올렸더니 **메모리로 먼저 죽었습니다.** `MEMORY_LIMIT` 기본값이 낮아서 CPU 장애가 나기 전에 OOM 이 터진 겁니다. 반대로 `MEMORY_LIMIT` 을 크게 줬더니 이번엔 **교착**에 빠졌습니다."*
>
> *"**세 손잡이가 동시에 살아 있다**는 걸 늦게 알았습니다. 지금은 `run.sh` 가 **나머지 둘을 안전값으로 고정**하고 하나만 켭니다. 이걸 처음부터 했으면 시간을 많이 아꼈을 겁니다."*
>
> *"그리고 **측정값을 먼저, 해석을 나중에** 하겠습니다. 처음엔 '이게 OOM 이겠지' 하고 봤는데, 실제로는 로그가 **MemoryGuard 자진 종료**라고 말하고 있었습니다. **먼저 읽고 나중에 이름 붙이는** 순서가 맞습니다."*
